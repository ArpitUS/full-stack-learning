# Cross-Technology Integration Map

## Application Path

```text
React + TypeScript
    -> typed HTTP API calls
Go REST API
    -> validation, authentication, business rules
PostgreSQL + Redis
    -> durable data, cache, sessions, rate limits
Docker Compose
    -> repeatable local multi-service environment
CI/CD
    -> test, build, scan, publish, deploy
AWS or Kubernetes
    -> runtime, networking, storage, scaling
Terraform
    -> reproducible infrastructure
Observability
    -> logs, metrics, traces, performance investigation
```

## Learning Dependencies

| Foundation | Enables | Why it comes first |
| --- | --- | --- |
| Modules 01-02: Git and Linux | Every module | Learners need reproducible local work and reviewable Git history. |
| Modules 03-10: Go | Modules 11-15 | HTTP services and reliability require language, concurrency, and error fundamentals. |
| Modules 11-15: API development | Modules 16-25 and 30-33 | The data contract and backend boundaries guide database and frontend work. |
| Modules 16-25: PostgreSQL and Redis | Authentication, TeamOps features, performance | Correct durable data comes before cache and session behavior. |
| Modules 30-33: React and TypeScript | End-to-end TeamOps | The client should consume a stable API and model typed states. |
| Modules 37-41: Docker and CI/CD | AWS and Kubernetes | A tested, repeatable image is the unit that gets deployed. |
| Modules 42-56: AWS, security, Kubernetes | Modules 57-60 | Runtime, networking, and deployment context make operational signals meaningful. |
| Modules 57-66: observability through interviews | Production readiness | These modules use evidence generated by the working system. |

## TeamOps Reuse Rule

Use small isolated exercises to learn a concept. Reuse the validated pattern in TeamOps only when the concept has a clear product purpose. Record the integration in [TeamOps stages](../12-projects/teamops/STAGES.md), the relevant feature row, and the contribution tracker.
